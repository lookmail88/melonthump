# MelonThump 1.1.0 Design — Server ↔ Client Communication 1.1.0 设计文档——服务端 ↔ 客户端通信

> Status: design settled on 2026-10-24; implementation awaits the go-ahead. This document is the contract for the 1.1.0 release.
>
> 状态：2026-10-24 设计定版；实施等开工指令。本文件即 1.1.0 版本的实施契约。

> Theme: the 1.1.0 release focuses on one thing — the communication between the server and the iOS client. App version 1.1.0 (the 1.0.0 build is in App Store review).
>
> 主题：1.1.0 只做一件事——服务端与 iOS 客户端之间的通信。App 版本号 1.1.0（1.0.0 正在 App Store 审核中）。

## 1. Goals & Non-Goals 目标与非目标

Goals:

目标：

1. **Usage statistics with an ad-request ledger**: the client reports anonymous usage events; the server stores them in PostgreSQL. Ad lifecycle events double as our own ledger to reconcile against AdMob's dashboard numbers.

   **使用量统计 + 广告请求流水**：客户端上报匿名使用事件，服务端落 PostgreSQL。其中广告生命周期事件同时是自家流水账，用于与 AdMob 后台数字对账。

2. **Server-issued ad configuration**: at startup the app obtains the rewarded ad unit ID from the server instead of carrying the real ID in the binary.

   **服务端下发广告配置**：App 启动时从服务端取激励广告单元 ID，真实 ID 不再打进发布包。

3. **App Attest gating**: the config and reporting paths verify that requests come from a genuine app on a genuine Apple device.

   **App Attest 门控**：配置与上报通道验签，确认请求来自真机上的正版 App。

Non-goals:

非目标：

- No user details: no accounts, no names, no IDFA, no device fingerprints. One anonymous, regenerable install UUID is the only identifier.
- 不收用户细节：无账号、无姓名、无 IDFA、无设备指纹。唯一标识是一个匿名、可重置的安装 UUID。
- No version/device-model statistics in this release.
- 本版不做版本/机型分布统计。
- The **AdMob App ID stays in Info.plist** (injected from `Secrets.xcconfig`): the Google Mobile Ads SDK reads `GADApplicationIdentifier` from the bundle at startup and offers no runtime injection — this is an SDK hard requirement, not a choice.
- **AdMob App ID 留在 Info.plist**（由 `Secrets.xcconfig` 注入）：Google Mobile Ads SDK 启动时从包内读 `GADApplicationIdentifier`，无运行时注入接口——这是 SDK 硬性要求，不是取舍。

## 2. Current State 现状

- Server endpoints today: `GET /api/health`, `GET /api/v1/version/getclientversion` (version policy). Analysis is fully on-device; the server accepts no writes and holds no user data.
- 服务端现有端点：`GET /api/health`、`GET /api/v1/version/getclientversion`（版本策略）。分析全在本地；服务端不接受写入、不持有用户数据。
- The version-policy endpoint is verified healthy on prod (checked 2026-10-24 with the real path above; an earlier "prod 404" note was an artifact of probing a wrong path).
- 版本策略端点 prod 实测健康（2026-10-24 用上面真实路径验证；早前所谓“prod 404”是探错路径的误记）。
- Database config is already wired (2026-10-24, option A): a dedicated `melonthump` database + user inside the Retax PostgreSQL instances (`retax-dev` / `retax-prod` pods); credentials only in the `melonthump-db` k8s Secret per app namespace; both manifests inject `SPRING_DATASOURCE_URL/USERNAME/PASSWORD`. JDBC URL crosses namespaces: `jdbc:postgresql://postgres.retax-<env>.svc.cluster.local:5432/melonthump`. The server has no DB code yet — the env is inert until this release.
- 数据库配置已就位（2026-10-24，方案 A）：借 Retax 的两个 PostgreSQL 实例（retax-dev / retax-prod），内建专用 `melonthump` 库与用户；凭据只存各 app namespace 的 k8s Secret `melonthump-db`；两份 manifest 已注入 `SPRING_DATASOURCE_URL/USERNAME/PASSWORD`。JDBC 地址跨 namespace：`jdbc:postgresql://postgres.retax-<env>.svc.cluster.local:5432/melonthump`。服务端尚无 DB 代码——本版落地前这些 env 不生效。

### Backward compatibility (hard requirement) 向后兼容（硬性要求）

The server must keep supporting previous client versions. Rules:

服务端必须持续支持旧版客户端。规则：

1. **Additive-only changes** to existing responses: new fields are optional, and fields are never renamed, removed or retyped. (`rewardedAdUnitId` in §3.1 follows this — 1.0.0 clients decode the policy exactly as before; Swift Codable ignores unknown fields.)
   现有响应**只增不改**：新字段一律可选，字段永不改名、删除或改类型。（§3.1 的 `rewardedAdUnitId` 即按此规——1.0.0 客户端解码策略与今天完全一致；Swift Codable 自动忽略未知字段。）
2. **Existing endpoints keep their semantics**: `/api/v1/*` paths are never broken; a breaking change ships as `/api/v2/*` alongside, and v1 stays up until the version policy's `minSupportedVersion` has retired every v1 client.
   现有端点**语义不变**：`/api/v1/*` 永不破坏；破坏性变更以 `/api/v2/*` 并存发布，v1 保留到版本策略的 `minSupportedVersion` 把所有 v1 客户端退场为止。
3. **Gating applies only to new surface**: attestation is required for the new field and the new write endpoints; the legacy policy fetch and health check stay open exactly as today, so an un-updated client behaves identically before and after the 1.1.0 server deploys.
   门控**只加在新表面上**：验签只管新字段与新写接口；旧的政策拉取与健康检查保持今天的开放方式——1.1.0 服务端上线前后，未升级的客户端行为完全一致。
4. **Support window is a policy decision, not an accident**: how long an old version remains usable is governed deliberately by `minSupportedVersion` and the release sequence (§8), never by an unintended server break.
   支持窗口是**策略决定、不是事故**：旧版能用多久，由 `minSupportedVersion` 与发布顺序（§8）刻意控制，永不因服务端意外改坏而中断。

## 3. API Contracts 接口定义

### 3.1 Version policy — extended 版本策略（扩展现有端点）

`GET /api/v1/version/getclientversion?currentVersion=x.y.z` gains one optional field:

现有端点响应新增一个可选字段：

| Field 字段 | When 何时出现 | Meaning 含义 |
|---|---|---|
| `rewardedAdUnitId` | Only when the request carries a **valid App Attest assertion** (§6) 仅当请求带**有效 App Attest 断言**时 | The production rewarded ad unit ID 服务端下发的正式激励广告单元 ID |

- Requests without a valid assertion get exactly today's response (no field) — old clients are unaffected, and scrapers cannot harvest the real unit ID from a public endpoint.
- 无有效断言的请求拿到的响应与今天完全一致（无此字段）——旧客户端不受影响，爬虫也无法从公开接口薅到真实单元 ID。
- Client behaviour: if the field is present, AdsManager loads with it; if absent or the fetch fails, it falls back to Google's official test unit (the fallback rule already shipped in `development`, commit 1495531). The real ID never appears in the binary or in git.
- 客户端行为：字段在就用它加载广告；不在或请求失败则回退 Google 官方测试单元（回退规则已落地 development，commit 1495531）。真实 ID 不进二进制、不进 git。
- The real unit ID is server configuration (`MELONTHUMP_REWARDED_AD_UNIT_ID` env on the deployment), not code.
- 真实单元 ID 是服务端配置（Deployment 的 env `MELONTHUMP_REWARDED_AD_UNIT_ID`），不是代码。

### 3.2 Attest challenge 验签挑战

`POST /api/v1/attest/challenge` → `{ "challenge": "<base64>", "expiresInSeconds": 300 }`

- One-time, short-lived challenges, stored server-side **in PostgreSQL** (the `attest_challenge` table, §4) — prod runs **2 replicas**, so nothing request-scoped may live in pod memory; either pod must be able to verify what the other issued. The client hashes the challenge into the assertion's client data.
- 一次性、短时效，服务端存 **PostgreSQL**（`attest_challenge` 表，§4）——prod 跑 **2 副本**，请求级状态不能放 pod 内存；任一 pod 签发的 challenge 必须能被另一 pod 验证。客户端把 challenge 掺入断言的 client data 哈希。

### 3.3 Event reporting 事件上报

`POST /api/v1/stats/events` — requires a valid assertion (§6). Batch upload:

需有效断言（§6）。批量上报：

```json
{
  "installId": "3f6b0f5e-…-uuid",
  "events": [
    { "type": "analysis_completed", "clientTs": 1790000000123, "verdict": "RIPE" },
    { "type": "ad_requested",  "clientTs": 1790000000456, "slot": "rewarded_main", "unitSource": "server" },
    { "type": "ad_loaded",     "clientTs": 1790000000789, "slot": "rewarded_main" },
    { "type": "ad_load_failed","clientTs": 1790000000789, "slot": "rewarded_main", "errorCode": 3 },
    { "type": "ad_shown",      "clientTs": 1790000001000, "slot": "rewarded_main" },
    { "type": "ad_rewarded",   "clientTs": 1790000009000, "slot": "rewarded_main" },
    { "type": "ad_dismissed",  "clientTs": 1790000009100, "slot": "rewarded_main" }
  ]
}
```

Response: `202 { "accepted": 7 }`. The server stamps its own receive time on every row — **dual timestamps** (client occurrence time + server receive time, both stored; UTC storage, America/Los_Angeles aggregation).

响应：`202 { "accepted": 7 }`。服务端给每行打上自己的接收时间——**双时间戳**（客户端发生时间 + 服务端接收时间，UTC 存储、按美西时区聚合）。

Event types (v1, closed set):

事件类型（v1，封闭集合）：

| Type 类型 | Payload 载荷 | AdMob counterpart 对应 AdMob 指标 |
|---|---|---|
| `analysis_completed` | `verdict`: UNRIPE / RIPE / OVERRIPE / UNKNOWN | — |
| `ad_requested` | `slot`, `unitSource`: server / test_fallback | Requests 请求数 |
| `ad_loaded` | `slot` | (matched) 匹配成功 |
| `ad_load_failed` | `slot`, `errorCode` | (unmatched) 未匹配 |
| `ad_shown` | `slot` | Impressions 展示数 |
| `ad_rewarded` | `slot` | Rewarded completions 看完 |
| `ad_dismissed` | `slot` | — |

Rules: no audio, no frequency/debug data, no free-text fields. `slot` is a logical name — never the real ad unit ID.

纪律：不上报录音、不上报频率等调试数据、无自由文本字段。`slot` 是逻辑名——永不写真实广告单元 ID。

### 3.4 Reconciliation summary 对账汇总

`GET /api/v1/stats/summary?days=30` → per-day rows (America/Los_Angeles): analyses, verdict distribution, ad requests / loaded / failed / shown / rewarded, distinct active installIds. Read-only; protected by an admin token env (`MELONTHUMP_STATS_ADMIN_TOKEN`); also visible via SQL directly.

按日（美西时区）返回：分析次数、判定分布、广告请求/加载成功/加载失败/展示/看完、当日活跃 installId 数。只读；用管理 token（env `MELONTHUMP_STATS_ADMIN_TOKEN`）保护；也可直接 SQL 查。

Reconciliation note: our client-side counts and AdMob's will differ by small percentages (different counting rules and report timezones). The ledger's value is spotting **large** gaps — e.g. the fallback silently swallowing real traffic, or an SDK/AdMob outage.

对账须知：自家计数与 AdMob 因计数口径与报表时区不同，差个位数百分比属正常。自家流水的价值是发现**大缺口**——比如回退逻辑悄悄吞了真实流量、或 SDK/AdMob 侧故障。

**Addition (2026-10-24, as implemented): client version + channel.** Every client request carries an `X-App-Version` header; the stats upload envelope additionally carries `appVersion` and `channel`, stored per event (Flyway `V2` adds nullable `app_version` / `channel` columns to `app_event`; earlier 1.1.0 clients omit them and aggregate under `unknown`). Channel is computed on-device from the App Store receipt, following the project's channel rules: `xcode` (Debug builds) / `testflight` (sandbox receipt) / `appstore` (store receipt). Both values are client-reported and analytics-grade only — never a trust input. The summary gains per-day `channelInstalls` (distinct installs per channel) and `versionEvents` (event counts per version). This narrows the earlier "no version/device statistics" line to: no device statistics; version + channel only.

**补充（2026-10-24，随实现落地）：客户端版本 + 渠道。** 每个客户端请求带 `X-App-Version` 头；统计上报信封另带 `appVersion` 与 `channel`，逐事件落库（Flyway `V2` 给 `app_event` 加可空列 `app_version` / `channel`；早期 1.1.0 客户端不带，汇总时归入 `unknown`）。渠道由客户端按本项目渠道规则、依 App Store 收据在本地算出：`xcode`（Debug 构建）/ `testflight`（sandbox 收据）/ `appstore`（商店收据）。两值均为客户端自报、只作运营统计，永不作信任依据。汇总新增按日的 `channelInstalls`（各渠道去重活跃安装数）与 `versionEvents`（各版本事件数）。此前"不做版本/设备统计"的口径收窄为：不做设备统计，只收版本 + 渠道。

## 4. Data Model 数据模型

```sql
CREATE TABLE app_event (
    id            BIGSERIAL PRIMARY KEY,
    install_id    UUID        NOT NULL,
    type          VARCHAR(32) NOT NULL,
    verdict       VARCHAR(16),
    slot          VARCHAR(32),
    unit_source   VARCHAR(16),
    error_code    INTEGER,
    client_ts     TIMESTAMPTZ NOT NULL,
    received_ts   TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_app_event_received ON app_event (received_ts);
CREATE INDEX idx_app_event_type_received ON app_event (type, received_ts);
CREATE TABLE attest_key (
    key_id        VARCHAR(64) PRIMARY KEY,   -- App Attest key identifier
    install_id    UUID NOT NULL,
    public_key    BYTEA NOT NULL,            -- verified at enrollment
    sign_count    BIGINT NOT NULL DEFAULT 0, -- anti-replay counter
    environment   VARCHAR(16) NOT NULL,      -- production / develop
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE TABLE attest_challenge (
    challenge     BYTEA PRIMARY KEY,
    expires_at    TIMESTAMPTZ NOT NULL,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

- Flyway migration `V1__app_event_and_attest_key.sql` creates all three tables. Expired challenges are deleted opportunistically on insert. Boot 4 note: Flyway needs the `spring-boot-starter-flyway` module on the classpath or migrations silently never run (house lesson, see AGENTS.md).
- Flyway 迁移 `V1__app_event_and_attest_key.sql` 建三张表。过期 challenge 在插入时顺手清理。Boot 4 注意：必须引 `spring-boot-starter-flyway`，只放 flyway-core 不会触发迁移（本机教训，见 AGENTS.md）。
- Retention: none for now (volume is tiny); revisit if the table ever grows past ~1M rows.
- 保留期：暂不设（量极小）；表超过约 100 万行再议。

## 5. App Attest Flow 验签流程

Enrollment (once per install, on first launch that needs it):

注册（每个安装一次，首次需要时）：

1. Client: `DCAppAttestService.generateKey` → `attestKey(keyId, challengeHash)` → sends attestation object to the server.
2. Server: verifies the attestation against Apple's App Attest root CA (certificate chain, nonce/challenge match, app ID check), stores the public key in `attest_key` (§4).

   服务端：用苹果 App Attest 根 CA 验 attestation（证书链、challenge 匹配、App ID 校验），公钥存 `attest_key`（§4）。

Assertions (per config fetch / event batch):

断言（每次取配置/上报时）：

1. Client fetches a challenge (§3.2), then `generateAssertion(keyId, clientDataHash)` where the hash covers the challenge + a hash of the request body.
2. Server verifies the signature with the stored public key, checks the challenge is fresh and the sign counter is strictly increasing (anti-replay).

   服务端：用已存公钥验签，校验 challenge 时效与签名计数器严格递增（防重放）。

Environment matrix (matches the house channel rules):

环境矩阵（与渠道三段式规则一致）：

| Build 构建 | Attestation env 环境 | Backend 后端 | Server accepts 服务端接受 |
|---|---|---|---|
| Xcode install 开发装机 | develop | dev | develop + production |
| TestFlight | production | prod (default 默认) | production only |
| App Store | production | prod (locked 锁死) | production only |

Prerequisites & limits:

前提与限制：

- The App ID needs the **App Attest capability enabled** in the developer portal (one user action, before the first TestFlight build of 1.1.0).
- App ID 需在开发者后台**开启 App Attest capability**（用户亲手操作；1.1.0 首个 TestFlight 构建之前完成）。
- Simulator cannot attest: the dev backend additionally accepts a debug bypass header **only when built/deployed as dev**; prod never honours it.
- 模拟器无法 attestation：dev 后端额外接受一个调试绕过头，**仅 dev 部署生效**，prod 永不认。
- Verification is fully offline (Apple root CA) — no per-request call to Apple.
- 验签全程离线（苹果根证书），不逐请求问苹果。

Failure policy: a failed attestation never blocks thumping. Config fetch falls back to the test unit; event batches stay queued and retry (and are dropped unreported if the queue overflows — statistics degrade, the user experience never does).

失败策略：验签失败永不阻断拍瓜。取配置失败走测试单元回退；事件批次留在队列重试（队列溢出则丢弃不报——统计可降级，用户体验不降级）。

## 6. Client Changes 客户端改动

- `AttestManager`: key lifecycle (generate → enroll → assert), keyed to the selected backend.
- `AttestManager`：密钥生命周期（生成 → 注册 → 断言），跟随所选后端。
- `StatsReporter`: appends events from two hook points — `LocalAnalyzer` completion (verdict) and `AdsManager` callbacks (ad lifecycle). Local persistent queue (file in app support dir); flush on launch, on reaching 20 events, and on entering background; exponential backoff; queue cap 500, drop-oldest.
- `StatsReporter`：两个埋点攒事件——`LocalAnalyzer` 出结果（判定）与 `AdsManager` 回调（广告生命周期）。本地持久队列（应用支持目录文件）；启动时、攒满 20 条、进后台时各刷一次；指数退避重试；队列上限 500，满了丢最旧。
- `installId`: random UUID created on first launch, stored in `UserDefaults` (deliberately **not** Keychain — deleting the app resets the identity; statistics must not survive uninstall).
- `installId`：首次启动生成随机 UUID，存 `UserDefaults`（刻意**不用** Keychain——删 App 即重置身份；统计身份不应熬过卸载）。
- VersionGate flow: the policy fetch now also carries the assertion when enrolled (extra challenge round-trip inside the existing 3-second launch window; fail-open unchanged).
- VersionGate 流程：拉策略时若已注册则附带断言（在现有 3 秒启动窗内多一跳 challenge；fail-open 不变）。

## 7. Server Changes 服务端改动

- Dependencies: `spring-boot-starter-jdbc` + `org.postgresql:postgresql` + `spring-boot-starter-flyway` (Boot 4 split: flyway starter required, see §4 note).
- 依赖：`spring-boot-starter-jdbc` + `org.postgresql:postgresql` + `spring-boot-starter-flyway`（Boot 4 拆分：必须 flyway starter，见 §4 注）。
- **Replicas: prod runs 2 pods (dev stays at 1)** — for availability and zero-downtime rollouts, not for load. Consequence: all request-path state (challenges, sign counters) lives in PostgreSQL; pod memory holds nothing that a request needs.
- prod 跑 **2 副本**（dev 保持 1）——为了可用性与滚动更新零中断，不是为了性能。后果：请求路径上的状态（challenge、签名计数器）全在 PostgreSQL，pod 内存不放任何请求所需状态。
- New code: `AttestController` (challenge + enrollment), attestation/assertion verification service (CBOR parsing; a maintained Java App Attest library or a minimal in-house verifier — decision at implementation time), `StatsController` (events + summary), `AppEventRepository` (JdbcTemplate), config field on the version-policy response.
- 新增代码：`AttestController`（challenge + 注册）、attestation/assertion 验签服务（CBOR 解析；用维护中的 Java App Attest 库或最小自研验签——实施时定）、`StatsController`（上报 + 汇总）、`AppEventRepository`（JdbcTemplate）、版本策略响应加字段。
- New env: `MELONTHUMP_REWARDED_AD_UNIT_ID` (prod only; dev keeps using test units), `MELONTHUMP_STATS_ADMIN_TOKEN`, `MELONTHUMP_ATTEST_ACCEPT_DEVELOP` (true on dev, false on prod).
- 新增 env：`MELONTHUMP_REWARDED_AD_UNIT_ID`（仅 prod；dev 继续用测试单元）、`MELONTHUMP_STATS_ADMIN_TOKEN`、`MELONTHUMP_ATTEST_ACCEPT_DEVELOP`（dev 为 true、prod 为 false）。
- Local verification gate: `mvn clean install` must pass before any commit (house rule).
- 本地验证门：任何 commit 前 `mvn clean install` 必须通过（定规）。

## 8. Release Sequence 发布顺序

Fixed order (also recorded in 《商业运营.md》 §4). **Updating the prod server version is the last step.**

定版顺序（《商业运营.md》 §4 亦有记录）。**更新 prod 服务端版本是最后一步。**

1. Land everything on `development`; semantic-release cuts the server version; the dev workflow builds and pushes the image; verify end-to-end on dev (incl. simulator bypass and a real-device develop attestation).
2. iOS: bump `MARKETING_VERSION` to 1.1.0, archive, upload, TestFlight soak (production-attestation path verified against the **dev-configured acceptance** or a staging check), then submit for review.
3. App Store: after approval, press **Release** — the new app version must actually be downloadable.
4. **Last step — promote the server to prod**: open the PR `development → main`, merge; ArgoCD rolls prod. This merge is what flips the policy's `latestVersion` to 1.1.0 (CI stamps it from `MARKETING_VERSION`) and starts VersionGate blocking 1.0.0 clients — safe only because step 3 already made 1.1.0 downloadable. Doing this step earlier would strand 1.0.0 users on a blocking screen with nowhere to upgrade.
5. Post-checks: prod policy shows `latestVersion 1.1.0`; first production events land in `app_event`; compare day-1 ad numbers with AdMob.

1. 全部改动落 `development`；semantic-release 定服务端版本；dev workflow 构建推镜像；dev 环境端到端验证（含模拟器绕过与真机 develop 环境验签）。
2. iOS：`MARKETING_VERSION` 升 1.1.0，Archive 上传，TestFlight 浸泡（生产环境验签链路验证），送审。
3. App Store：过审后点 **Release**——新版必须真的能下载。
4. **最后一步——服务端进 prod**：开 PR `development → main` 并合并，ArgoCD 滚动 prod。这次合并才是把策略 `latestVersion` 翻成 1.1.0 的动作（CI 从 `MARKETING_VERSION` 注入），VersionGate 自此开始拦 1.0.0 客户端——只有第 3 步已完成时才安全。提前做这步，1.0.0 用户会被全屏拦住却无处升级。
5. 收尾核查：prod 策略 `latestVersion` 为 1.1.0；首批生产事件落 `app_event`；首日广告数字与 AdMob 对一遍。

## 10. Test Plan 测试计划

- Server: unit tests for attestation verification (Apple's published test vectors), event validation, summary aggregation across the PT day boundary.
