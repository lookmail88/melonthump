## 科学依据（v1 固定阈值的底气）
- 西瓜成熟过程中**共振频率下降、阻尼变化**：熟瓜敲出低沉浑圆的"嘭嘭"声，
  生瓜偏高偏脆，过熟的阻尼急剧增大、声音发闷发"噗"。
  （声学测量厂商 BKSV 的公开解释；多篇水果声学无损检测论文结论一致。）
- Zeng 等人 2014 年的手机 App 研究：用拍击声区分生/熟，
  测试集准确率 91%–98%。
- Pintor 等人的 Android App：综合准确率约 86%，
  在瓜的赤道部位拍击时约 93%；甜度越高频率越低。
- 结论：**主频 + 衰减（阻尼）** 两个特征做固定阈值三档分类，
  v1 在工程上是站得住的；阈值先用文献值起步，靠自测校准收敛。

## v1 范围
- App 端：录音（拍击 3–5 下，引导用户拍赤道部位）、上传；
  不做端侧推理，模型/阈值更新走服务端。
- 服务端：接收音频 → 提特征（主频、频谱质心、衰减系数）
  → 固定阈值判三档 → 返回结果；**分类器做成接口**，
  以后换 ML 模型只换实现类；Swagger 文档必备。
- 不做：用户账号体系（v1 可匿名/设备 ID）、支付、社交功能。
- 广告（AdMob）：用户在考虑，未定进 v1 还是后加；UI 设计时预留广告位。

## 架构（对齐 Retax 经验）
- **服务端**：Spring Boot（与 Retax 同栈：OpenJDK 25 + Boot 4.x），
  跑在 homelab k3s；API 文档 springdoc-openapi（用户明确要求）。
- **客户端**：iOS SwiftUI（Retax 客户端同套路：录音、上传、结果展示）。
- **部署**：GitOps 同 Retax（分支 → ArgoCD）；仓库 public，
  但部署密钥/域名配置与代码分离，不进 public repo。
- API 草案：`POST /api/v1/thump`（multipart 音频）
  → `{ dominantFrequencyHz, dampingRatio, verdict: UNRIPE | RIPE | OVERIPE, confidence }`。

## 数据标注计划（v1 之后，"慢慢做"）
- 最难的是 ground truth：成熟度只能**切开看**。
- v1 内置"校准模式"：用户吃瓜前录音、切开后回填真实结果（生/正好/过熟），
  每次吃瓜都是一次标注——把日常变成数据采集。
- 阈值校准：先文献值 → 自测几十个瓜收敛 → 数据够了再训模型。
- 注意：public repo 公开模型和阈值不涉密；但**录音样本本身别进 repo**（体积），
  放对象存储或另行管理。

## 里程碑（建议）
- **M1**：server 脚手架（Spring Boot + Swagger + `GET /api/health`）+ iOS 录音上传壳，本地编译通过后 push。
- **M2**：音频上传 + 特征提取 + 固定阈值三档分类器（服务端可测）。
- **M3**：iOS 结果展示 + Stephanie 设计元素落地。
- **M4**：校准/回填模式上线，开始攒标注数据；AdMob 接入（如用户拍板）。
