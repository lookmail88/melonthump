## 1. The Model as a File (.ml) 分析模型文件化（.ml）

- **Goal**: lift the analysis model out of the code into a data file that the app loads at runtime — tuning parameters no longer means changing code.

- **目标**：把分析模型从代码里抽出来，变成数据文件，App 运行时加载——改参数不再改代码。

- **Current state**: every threshold and gate is hardcoded in `LocalAnalyzer.swift` (analyzer heuristic-v2.2: dominant frequency <160Hz overripe / 160–280Hz ripe / >280Hz unripe, plus a set of spectral-gate parameters).

- **现状**：判定阈值与门限硬编码在 `LocalAnalyzer.swift`（分析器 heuristic-v2.2：主频 <160Hz 过熟 / 160–280Hz 熟 / >280Hz 生，另有频谱门等一组参数）。

- **Naming (decided)**: the current model is named **Baby 1.0** — the heuristic-v2.2 parameter set once migrated into an .ml file, and the default entry in the model picker.

- **命名（已定）**：现行模型定名为 **Baby 1.0**——即 heuristic-v2.2 参数集迁入 .ml 文件后的正式名字，也是模型选择列表的首发默认项。

- **Requirements**:

- **要求**：

  - The model file uses the **.ml** extension and carries every threshold and gate parameter.

  - 模型文件扩展名定为 **.ml**，承载全部阈值与门限参数；

  - The app loads the model file at launch / analysis time; a missing or corrupt file falls back to built-in default parameters — **it must never crash**.

  - App 在启动/分析时加载模型文件；文件缺失或损坏时回退到内置默认参数，**不许崩**；

  - The file format is finalized during this release's design phase and must include a version field.

  - 文件格式在本版设计阶段定稿，必须带版本号字段；

  - The loading interface must leave a seam for swapping in a real machine-learning model later: same interface, replaceable implementation.

  - 加载接口要为将来替换成真正的机器学习模型留接缝：接口不变、实现可换；

  - Multiple models may coexist (different versions, different models); the user switches between them in the hamburger menu's model picker (see §2).

  - 模型可多份共存（不同版本、不同模型），用户在汉堡菜单的"模型选择"里切换（见 §2）；

  - Model files ship with app releases; whether they can also be delivered by the server is an open question below.

  - 模型文件随 App 版本发布更新；是否支持服务端下发更新列入待定事项。

- **Not in this release**: no trained CoreML model — this step is only "parameters as data".

- **本版不做**：不引入训练出来的 CoreML 模型，只做"参数即数据"这一步。

## 2. UI Upgrade (Structure & Interaction Only; Art Frozen) UI 升级（只动结构与交互，美术冻结）

- **Art freeze (hard rule)**: Stephanie's original artwork — the watermelon, every cat's design, the color palette, all existing screen elements — **stays completely untouched, not one pixel redrawn**. New elements follow the app's existing design language; no foreign style is introduced.

- **美术冻结（硬性要求）**：Stephanie 的原创美术设计——西瓜、每只猫的造型、配色、现有画面元素——**完全不动，一像素不改**。新增元素的视觉风格参照 App 现有设计语言，不引入外来风格。

- **Top bar**:

- **顶部栏改造**：

  - **Top-left**: a hamburger button (three lines; interaction modeled on the Muse app's top-left menu button).

  - **左上角**：汉堡菜单按钮（三条横线，交互形态参照 Muse App 左上角的菜单按钮）；

  - **Top-right**: an Invite button (entry point modeled on the Muse app's top-right invite button).

  - **右上角**：Invite 按钮（入口形态参照 Muse App 右上角的邀请按钮）；

  - The top bar must not cover any existing artwork; exact placement is mocked up in the design phase and built only after the user's confirmation.

  - 顶部栏不得遮挡原有美术元素，具体位置在设计阶段出图，经用户确认后再施工。

- **Hamburger menu**: tapping opens a slide-in drawer. Decided contents: a **Model picker** — switches the .ml model used for analysis (paired with the model-as-file work in §1), persisted locally and effective from the next analysis; a **Settings** entry — Language lives under Settings (see below); an **About** entry (app version, privacy policy, terms of service, contact / feedback). Remaining candidate: history; finalized in the design phase.

- **汉堡菜单**：点击展开侧边抽屉式菜单。已定内容：**模型选择选项**——切换分析所用的 .ml 模型文件（与 §1 模型文件化对应），选择本地持久化、对下一次分析即时生效；**Settings（设置）选项**——Language（语言）归入 Settings 之下（见下条）；**About（关于）选项**（内容：App 版本号、隐私政策、服务条款、联系/反馈入口）。其余候选：历史记录，设计阶段定稿。

- **Languages (i18n)**: app UI strings ship in three languages — **Simplified Chinese, English, Español**. The default follows the system language; switching under Hamburger → Settings → Language persists locally, takes effect immediately, and needs no app restart. Scope is UI text strings only; text baked into artwork is out of scope (art freeze).

- **多语言（i18n）**：App UI 文案支持三种语言——**简体中文、English、Español**。默认跟随系统语言；用户在汉堡菜单 → Settings → Language 里切换后，本地持久化、即时生效、不重启 App。本地化范围只限 UI 文案字符串，美术图内嵌的文字不在范围内（美术冻结）。

- Any structural change beyond the top bar is listed item by item in the design phase and built only after the user's item-by-item confirmation — nothing is done first and reported later.

- 顶部栏之外的界面结构如需调整，设计阶段逐项列出、逐项经用户确认，不先斩后奏。

## 3. Invite (Modeled on Muse's Invite) Invite 功能（机制参照 Muse 的邀请）

Modeled on Muse's invite mechanism, an isomorphic feature for MelonThump:

参照 Muse 邀请机制，为 MelonThump 设计同构的功能：

- **Invite credentials**: every user has their own invite credential in two forms — an invite link and an invite code.

- **邀请凭据**：每个用户有自己的邀请凭据，两种形态——邀请链接 + 邀请码；

- **Sharing**: tapping the top-right Invite button opens the system share sheet; the link / code goes out over Messages, WeChat, Mail, and other system channels.

- **分享路径**：点右上角 Invite 按钮 → 拉起系统分享面板，把邀请链接/邀请码经短信、微信、邮件等系统渠道发给朋友；

- **Invitee path**: a friend installs and opens the app via the invite link, or enters the invite code in the app → the system confirms one valid invite. Sharing, installing, and confirming are three separate steps; merely opening the link does not count as confirmation.

- **被邀请人路径**：朋友通过邀请链接安装并打开 App，或在 App 内输入邀请码 → 系统确认一次有效邀请。分享、安装、确认是三个独立步骤，点开链接本身不算确认；

- **Reward**: once an invite is confirmed, the inviter is rewarded in the app's credits, wired into the existing CreditWallet. Whether the invitee is also rewarded, the amounts, the per-user invite cap, and what counts as a "valid invite" (e.g. the invitee completes a first tap analysis) are numbers to be set in the design phase, calibrated together with the existing credit economy (analysis costs 1, welcome grant 5, daily earn cap 10).

- **奖励**：邀请确认成立后给邀请人发放奖励，币种为 App 内的 credit，与现有 CreditWallet 打通。被邀请人是否同时得奖励、双方数额、每人邀请上限、"有效邀请"的确认条件（如被邀请人完成首次拍瓜分析），数值在设计阶段定，并与现有 credit 经济参数（分析扣 1、欢迎赠 5、日上限 10）一并校准；

- **Anti-abuse**: invite confirmations must be recorded and verified server-side (reusing the stats persistence and App Attest gating built in 1.1.0); duplicate invites from the same device / install are never double-counted.

- **防刷**：邀请确认必须经服务端记录与校验（复用 1.1.0 已建的统计落库与 App Attest 门控）；同一设备/同一安装的重复邀请不重复计奖；

- **Privacy boundary**: an invite is install attribution plus a reward — no user data is shared with anyone.

- **隐私边界**：邀请只是安装归因 + 发奖，不涉及任何用户数据互通。

## 5. Standing Rules 不变的规矩

- Server backward compatibility: response fields are only ever added as optional; `/api/v1` semantics never break.

- 服务端向后兼容：只增可选字段、`/api/v1` 语义永不破；

- Release order: server code deploys first (policy pinned to the old version) → TestFlight verifies against prod → App Store submission, review, manual release → version policy flips only after the new build is downloadable.

- 发布顺序：服务端代码先行部署（策略钉住旧版）→ TestFlight 连 prod 验证 → App Store 提交过审、手动发布 → 新版可下载后才翻版本策略；

- Local build and the full test suite must pass before any commit; work happens only on the development branch, and main accepts PRs only.

- 本地编译/全量测试通过才能 commit；只在 development 分支施工，main 只接受 PR。
